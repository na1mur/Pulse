## Plan

### Slices (one backend-engineer, in order; test first; each slice leaves checks green)
1. Primitives (`src/domain` + `src/modules/auth`): password hashing (recommendation: `node:crypto` scrypt with per-hash salt and stored parameters, no native dependency; constant-time compare; a dummy hash verified on unknown emails so timing does not reveal them), 8-128 character rule, access tokens (HS256 JWT with `JWT_SECRET`, 15 min; library choice is yours, pure JS, exact pin), refresh tokens (random, HMAC-SHA-256 with `REFRESH_SECRET` stored as the 32-byte hash), email tokens (random, stored hashed, single use, 24 h verify, 1 h reset later). Unit tests.
2. Registration and verification: `auth.register` (uniform answer whether or not the email exists, never reveals; existing verified account gets no second mail; creates user + `user_revisions` row + default preferences in one transaction; sends the verification mail after commit, a send failure is logged and the user can resend), `auth.verifyEmail` (expired, used or unknown tokens refused with the uniform error; single use enforced atomically), `auth.resendVerification` (at most once a minute per account, uniform response).
3. Sessions: `auth.login` (uniform `UNAUTHENTICATED` for wrong email or password, `FORBIDDEN` only for right password + unverified, per-IP and per-account rate limits with `RATE_LIMITED`, device registration/upsert with the decision above), `auth.refresh` (rotation in one atomic statement; reuse of a rotated token revokes the whole family and the device; expired/revoked refused; lifetime extended), `auth.logout` (revokes this device's credentials), auth guard for `auth: 'user'` operations (verifies the access token and that the device is not revoked; sets the log user), `auth.getMe`.
4. First sign-in setup (AUTH-12, TAG-07, US-6.1): completing setup confirms the timezone (IANA, R-15, never changed silently) and creates the starter tags exactly once (Deep Work, Learning productive; Meeting, Admin, Break neutral; Gaming, Social Media leisure linked to gaming/social classes), idempotent by command ID (R-34, D-30: this one carries a command ID; the idempotency store holds no raw tokens), revision bump, replays return the original result. Wire `MailModule` and the auth module into `AppModule`.

### Interfaces
Contract operations as defined; link path constants from `src/mail/mail-links.ts`; `AuthGuard` + `@CurrentUser()` decorator other modules will use; `RevisionService.bump(tx, userId)` used by every later write; rate limiter as a small injectable (in-memory, bounded, keyed by IP / account hash, clock injected).

### Review focus
- Refresh rotation race: two concurrent refreshes with the same token (exactly one wins, the other triggers family revocation or is refused consistently); reuse detection; family revocation is atomic.
- Enumeration: register, resend, login, verify error bodies, status codes and timing are identical for known and unknown emails.
- Token storage: nothing raw in the database, logs, idempotency store or error bodies; constant-time comparisons; `alg` confusion on the JWT (only HS256, no `none`).
- Email tokens: single use under concurrency, expiry boundary, used-token replay, token for another purpose refused.
- Rate limits cannot be bypassed with spoofed `X-Forwarded-For` (TRUST_PROXY), case/Unicode variants of the email, or by unbounded memory growth.
- Verified-only login; starter tags created once under replay and concurrency; timezone validation.
- Transactions: user + revisions + preferences atomic; mail sent after commit.
