## 7. Operations & events (contract at capability level)

One contract source defines every operation, event and error. Server validation and the typed client are **generated from it**. Every incoming message is validated, including realtime messages.

### 7.1 Conventions

- Every response carries **server time**; every write carries a **command ID** (R-34) and, when replayed from the outbox, its occurred-at time.
- Errors have one shape: `code`, human-readable `message`, optional `details` (field errors, conflicting session ID) and `requestId`.
  Codes: `VALIDATION`, `UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT` (overlap, name taken, stale revision), `RATE_LIMITED`, `UNAVAILABLE`, `INTERNAL`.
- Lists use cursor pagination. Durations are integer seconds; instants are ISO-8601 UTC; days are `YYYY-MM-DD`; credits are decimals with 2 places.
- Every resource access is checked against the authenticated user.

### 7.2 Operations

| Group | Operations |
|---|---|
| Auth | register, verify email, resend verification, login, sign in with Google, refresh, logout (this device), list devices, revoke device, change password, change email (+ confirm), request reset, reset password, get me, complete first sign-in (timezone), delete account |
| Timer | get timer; **start** (title?, tag?, startedAt? for offline replay); **pause** (endedAt? for offline replay); **update running** (title?, tag?); switch, discard (P2) |
| Sessions | list (range, tag?, category?, text?, cursor); get; create manual; update (title, tag, summary, start, end); delete |
| Tags | list; create (name, category; name taken → `CONFLICT`); rename; recategorize; set distraction class; archive; unarchive; delete (replacement tag or Untagged) |
| Goals | get current and history; set (kind, minutes or unset) |
| Preferences | get; update account preferences |
| Stats | **today snapshot** (running session, today's total and productive time, goals, streaks, balance); period stats (day / week / month: headline numbers, per-day stacked series, breakdowns by category and tag, tracked minutes, goal days); day timeline |
| Usage | **report increments** (batch; each increment by its command ID) |
| Credits | balance snapshot (balance, rates); ledger (range, cursor); balance series (range); get / set rates |
| Achievements | list recent / unnotified; mark notified (per device) |
| Push | register / clear this device's push token |
| Sync | state snapshot; changes since revision (including tombstones); subscribe to the event stream |
| Data | export all (JSON); export period (CSV: sessions, daily summary); import (legacy migration, P1) |
| App updates | latest version per platform (version, download URL, signature or checksum) |
| Health | `/health` (API and database status); liveness |

Commands and mutations return the resulting state **and the new revision**, so the caller needs no follow-up reads.

### 7.3 Events (server to all of the user's devices)

`timer.changed` (started, paused, title or tag changed), `session.upserted`, `session.deleted`, `tag.upserted`, `tag.deleted`, `goals.changed`, `preferences.changed`, `achievement.unlocked` (goal reached), `credits.changed` (new balance snapshot), `credentials.revoked` (forces sign-out on that device). Every event carries the revision. Clients never send state over the realtime channel; they send commands through the normal operations.

## Plan

### Slices

1. **Contract package** (`packages/contract`, package `@pulse/contract`) - backend-engineer - Vitest: schemas accept valid and reject invalid examples (limits, formats, error codes); every catalogue entry is either fully specified or marked name-only; every event schema carries the revision; generation is deterministic (running it twice gives no diff).
   - zod schemas: primitives (IDs, ISO-8601 UTC instants, `YYYY-MM-DD` day keys, integer-second durations, 2-decimal credit amounts, IANA timezone, cursor pages), the error model (7.1: `code` enum of the 8 codes, `message`, `details?`, `requestId`), the command envelope (command ID, occurred-at), response conventions (server time; new revision on mutations), section 6 entities as wire DTOs, section 7.2 operations per D-29, section 7.3 events with the realtime message envelope (server to client events; client to server only connection-level messages such as auth, never state).
   - One operation catalogue (name, group, HTTP method and path, request, response, errors, name-only flag) that every generator reads.
   - Generators (`pnpm --filter @pulse/contract generate`): OpenAPI (a version the Rust generators of slice 3 accept) and JSON Schema into `packages/contract/generated/`; a typed TS client into `generated/`; a mock server (`pnpm --filter @pulse/contract mock`) answering every fully specified operation with schema-valid data and pushing example events over WebSocket.
   - ADR `docs/decisions/0003-contract-wire-format.md`: library choices, routes and versioning, where server time and revision travel, the realtime message format, how name-only operations appear.
2. **Server stub** (`apps/server`) - backend-engineer, after slice 1 - Vitest with HTTP requests: a request failing validation returns the 7.1 error shape with `VALIDATION` and a `requestId`; an unknown route returns `NOT_FOUND` in the same shape; `/health` and liveness answer per the contract with server time; one contract operation is stubbed end to end through the contract-driven validation (no business logic). The server's handler types come from the contract, so a contract change breaks the server's type check.
3. **Rust contract types** (`crates/contract-types`, crate `pulse-contract-types`) - core-engineer, after slice 1 - generated with `typify` (types) and `progenitor` (typed client), or the closest working equivalents, into `src/generated/` from slice 1's output; regenerated by one documented command; `crates/core` depends on it, and a test deserializes the example payloads of every fully specified operation and event (cross-language conformance).
4. **Checks** - devops-engineer, after 1-3 - `scripts/check.mjs`: a "generated contract is up to date" step (regenerate, then fail on any diff under `generated/`) in the right groups; a mock-server smoke start; dependency-cruiser rules for `packages/contract` (no app imports; the desktop UI imports types only) as far as the existing config allows without editing it, otherwise reported; CI picks the steps up through `check.mjs`; `CLAUDE.md` Commands lines for generate and mock.

### Interfaces

- `@pulse/contract` exports: the zod schemas and their inferred TS types, the operation catalogue, the event union, the error code enum. `package.json` scripts: `generate`, `mock`, `typecheck`, `test`, `build`.
- Generated outputs (exact names fixed in slice 1 and listed in its report): `packages/contract/generated/openapi.json`, `packages/contract/generated/json-schema/`, `packages/contract/generated/client/`. Slice 3 reads only these files, never the zod sources.
- `crates/contract-types`: `src/generated/` plus a hand-written `src/lib.rs` that re-exports it; added to the Cargo workspace; `crates/core` depends on it.
- The server's validation pipe and exception filter live in `apps/server/src` (transport layer) and import only `@pulse/contract`.

### Review focus

- One source: no hand-written duplicate of any shape on the server, in the TS client or in Rust.
- Spec fidelity: every 7.1 convention (server time on every response; command ID and occurred-at on every write; revision on every mutation result and event; the 8 error codes and the error shape; cursor pagination; integer seconds; UTC instants; `YYYY-MM-DD` days; 2-decimal credits) and the section 6 limits.
- D-29 boundary: no invented shapes for Stats, Credits, Usage, Achievements, Data.
- Realtime: clients never send state over the channel; events carry the revision.
- Determinism and the guard: generated output is stable, lives only under `generated/` (or carries `@generated`), and the up-to-date check catches drift.
- Rust generator limits (OpenAPI 3.0 vs 3.1, `oneOf` and discriminated unions, decimal and date formats) handled without hand-editing generated code.
