## Bugs
No Critical, High or Medium bugs.

### L1: actionlint skips shellcheck silently if the runner lacks it
- Severity: Low. Affected: plan ("actionlint (with shellcheck)").
- Evidence: actionlint 1.7.12 with `-verbose` and no shellcheck on PATH prints `Rule "shellcheck" was disabled` and still exits 0. The CI step runs without `-verbose`, so the log cannot show whether shellcheck ran. The step relies on the runner image's preinstalled shellcheck, and the image label is changing (L2).
- Impact: a future image without shellcheck would drop the `run:` script linting without any red signal.
- Fix: add `shellcheck --version` before `"$RUNNER_TEMP/actionlint"` (under `bash -e` it fails the job if shellcheck is missing), or pass `-verbose` and grep for the "disabled" line.

### L2: floating runner labels while the ubuntu-latest migration is under way
- Severity: Low (watch item). Every Linux job has the annotation "The ubuntu-latest label will migrate to Ubuntu 26 beginning October 19, 2026". These runs were still on `ubuntu-24.04` (image 20261012.334.1).
- Impact: the jobs depend on preinstalled tools: shellcheck (docs, L1), jq (ci, fails closed if missing) and the Android SDK (already deferred in the ledger). An image switch can turn CI red or quietly weaken it without any repo change, which works against "reproducible".
- Fix: pin `ubuntu-24.04` (and `windows-2025` or the current image) and move labels deliberately, or accept the floating labels and record that choice.

### L3: the comment "every push to main is checked to the end" is not quite true
- Severity: Low. `ci.yml` line 18.
- GitHub allows one running and one pending run per concurrency group. A new queued run cancels the existing pending one even with `cancel-in-progress: false`. Three quick pushes to `main` therefore cancel the second push's run before it starts. The newest commit is still checked, and `main` pushes bypass the ruleset anyway.
- Fix: correct the comment, or give pushes a unique group (for example `${{ github.workflow }}-${{ github.event_name == 'pull_request' && github.ref || github.sha }}`).

### L4: the Rust cache key depends on the runner's preinstalled stable Rust
- Severity: Low (performance only). The rust-cache configuration log lists the Rust versions it considered: `1.97.0` (pinned) and `1.99.1` (the image's default). Its key therefore changes whenever the Windows image bumps its stable Rust, which forces a cold build (4 to 5 min) even when `Cargo.lock` and the pin have not changed.
- Fix: `rustup toolchain uninstall stable` (or set the default to the pin) before rust-cache, or accept the cost.

### L5: two small doc gaps
- Severity: Low. (a) In `docs/knowledge/INDEX.md`, the update command `-X PUT .../rulesets/<id>` leaves out `--input .github/rulesets/main.json` and the live id 25812351. (b) The `docs/AGENTIC_SETUP.md` A6.1 item still says "Adapt the `ci-cd-and-automation` skill to this stack". The skill is unchanged (THIRD_PARTY "changes: none"), and the "Pending" list does not mention it, so its status is unclear.

### L6: watch items seen in the logs
- Severity: Low (not a T0.3 defect, logged so they are not forgotten).
- (a) Gradle prints "Deprecated Gradle features were used in this build, making it incompatible with Gradle 10" (run with `--warning-mode all` to find the source).
- (b) The pnpm store cache is saved from PR runs (`refs/pull/1/merge` and `refs/pull/2/merge`, about 53 MB per OS each), and other PRs cannot restore it. rust-cache and setup-gradle save only on `main`. Over time this wastes the 10 GB cache quota and evicts useful entries. Use `actions/cache/restore` on PRs and save only on `main`.
- (c) The repository setting `sha_pinning_required` is false, so SHA pinning is a convention rather than an enforced rule. Turning it on is an owner settings change, not a T0.3 requirement.

## Observations (not bugs)
- The bypass covers merging too. As a bypass actor the owner sees a red PR as BLOCKED, but the merge box offers "bypass rules", so the "blocked on red CI" guarantee holds for everyone except an admin who explicitly bypasses. That matches D-28.
- `require_extra_approval_for_unattributed_changes: true` is a server default that the repo JSON does not set. It did not affect PR #1 (`CLEAN`). Re-applying the file with PUT keeps the server default.
- No cache hits in either run. That is expected: PR-scoped caches are not shared between PRs, and nothing has run on `main` yet.
