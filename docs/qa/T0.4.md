## Bugs

### Bug 1: Body-parser errors answer INTERNAL instead of VALIDATION
- Severity: Medium
- Affected criterion: spec 7.1 error model (slice 2: errors outside handlers in the contract shape with the right code); R-36 downstream.
- Steps to reproduce: `pnpm --filter @pulse/server test src/app.body-errors.http.spec.ts` (new, fails both cases). By hand: start `apps/server/dist/main.js`, then `POST /v1/timer/start` with a JSON body over 100 KB, or with `Content-Encoding: br2`.
- Expected: 400 `VALIDATION` in the error shape (the filter's `CODE_BY_STATUS` already maps 413 and 415 to `VALIDATION`).
- Actual: 500 `INTERNAL`; the server logs `Unhandled error ... PayloadTooLargeError` with a stack for every such request. body-parser's errors are `http-errors` objects with `status`/`statusCode`, not Nest `HttpException`s, so `ContractExceptionFilter.toBody` never reaches its 413/415 mapping. Malformed JSON works only because Nest converts that one case.
- Impact: a client treats `INTERNAL` as a server fault and retries, so an oversized queued command would retry forever instead of becoming a sync issue (R-36); any client can fill the error log.

### Bug 2: Google re-authentication accepts only an ID token, which the Windows client never has
- Severity: Medium
- Affected criterion: D-31 ("changing the email and deleting the account require the password or a fresh Google sign-in"), AUTH-08, AUTH-06.
- Steps to reproduce: `auth.deleteAccount` body `{ "confirmation": "DELETE", "reauthentication": { "method": "google", "kind": "authorizationCode", "code": "c", "codeVerifier": "<43 chars>", "redirectUri": "http://127.0.0.1:5000/cb" } }` is rejected; only `{ "method": "google", "idToken": "..." }` passes (`packages/contract/src/operations/auth.ts`, `Reauthentication`).
- Expected: a fresh Google sign-in in either form the contract accepts for sign-in (`GoogleCredential`).
- Actual: ADR-0003 has the Windows app sign in with an authorization code + PKCE that the server exchanges, because only the server holds `GOOGLE_CLIENT_SECRET`, so the desktop never holds an ID token.
- Impact: a Google-only account cannot delete itself or change its email from Windows. One fix: make the Google variant carry a `GoogleCredential`. If T1.6 instead lets the desktop exchange the code itself, the code form of `auth.signInWithGoogle` should go too. The two must agree either way.

### Low (logged, not blocking)
1. `push.registerToken` and `push.clearToken` carry a command ID but answer 204 with no revision, while 7.2 says commands return the new revision. That's defensible, since the push token is device state that no event syncs. The spec or ADR-0003 should say so.
2. Spec 7.1 says "lists use cursor pagination". ADR-0003 returns tags, devices and goal history whole. The exception is recorded only in the ADR, not in the spec (section 11/13).
3. Mock server: the `requestId` in an error body differs from its `Pulse-Request-Id` header (`startMockServer` and `send` each call `randomUUID()`). The real server gets this right.
4. The server sends `X-Powered-By: Express`. Disable it with the T1.2 hardening.
5. Schema details for the feature tasks:
   - `CreditRates` allows negative amounts, though ADR-0003 says rates are non-negative (T5.1).
   - `TagName`'s `.trim()` is not in the JSON Schema, so Rust accepts `"   "` and rejects a valid padded 40-character name (VALIDATION from the server, harmless).
   - The catalogue names no error code for a used or expired email token on `verifyEmail`, `confirmEmailChange` and `resetPassword` (VALIDATION is the only fit; T1.4/T1.5 should state it).
