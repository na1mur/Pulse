# QA Report - T0.5 Time-math module (server and core) with the shared fixture suite
> Date: 2026-10-25 | Iteration: 1, re-checked in iteration 2 (see "Round 2": APPROVED)

## Recommendation
Round 1: REJECTED - one Medium bug. The core's `parse_instant` disagrees with the contract and the server on what an instant is: it accepts nine text forms the contract and the server reject (a leap second `23:59:60Z` silently becomes `:59`) and rejects valid contract instants with more than nine fractional digits (bug 1, reproduced by a new failing test). The acceptance bar itself passes. Every fixture is green in both implementations for UTC, Los Angeles, Dhaka, Auckland, Kathmandu and the 23 h / 25 h DST days, and so are the 67 cases QA added: the Apia skipped day, folds at midnight, a 15-minute skipped midnight, far past and far future years, long sessions and week boundaries. The four Low findings are logged, not blocking.

## Bugs

### Bug 1: Core `parse_instant` accepts non-contract instants and rejects valid ones
- Severity: Medium
- Affected criterion: D-19 (identical behaviour on both sides), the T0.5 Interfaces line "malformed day/instant -> a typed error, never ... a silent default", spec 7.1 `Instant`. The doc comment on `parse_instant` says it parses a contract `Instant` and rejects everything else.
- Steps to reproduce: `cargo test -p pulse-core --locked --test time_instant_parity`.
- Expected: same as the server's `parseInstant` and the contract's zod `Instant`. Reject all of these: `2026-10-25T08:30Z`, `2026-10-25 08:30:00Z`, `2026-10-25t08:30:00Z`, `2026-10-25T08Z`, `2026-10-25T23:59:60Z`, `2026-10-25T08:30:00,5Z`, `20261025T083000Z`, `+002026-10-25T08:30:00Z`, `-000001-01-01T00:00:00Z`. Accept `2026-10-25T08:30:00.1234567891Z` (any number of fractional digits) and floor it to 1792917000.
- Actual: the core accepts all nine. The leap second becomes `1792972799` (`23:59:59`), `T08Z` becomes 08:00:00, and the others parse silently. It returns `MalformedInstant` for 10+ fractional digits, which the contract accepts and the server floors.
- Impact: the core can store or replay an instant the server rejects as `VALIDATION`, which ends as a sync issue for something the client accepted. It can also reject a valid instant from the wire. Only the core's own `ends_with('Z')` check stands between jiff's lenient parser and the store. Likely fix: check the shape the server's regex enforces before handing the text to jiff, and drop fraction digits past the ninth (flooring stays exact). The new test pins both directions.

### Low (logged, not blocking)
1. **A fold that moves the local date backwards gives a negative row on both sides.** America/St_Johns, Goose_Bay and Moncton fell back at 00:01 until 2006-2010, and Antarctica/Casey on 2010-03-05. A session that starts in the repeated 23:xx after the first midnight produces a row with negative seconds and a second row that starts before the session. Example: St_Johns `2010-11-07T03:00:00Z`-`04:00:00Z` gives `{2010-11-06, -1800 s}` then `{2010-11-07, 02:30Z-04:00Z, 5400 s}`. The total is still right. Both implementations do the same thing, and Python reproduces it. ADR-0004 doesn't say which day such an instant belongs to: `dayKey` says the old date, `dayBounds` the new one. No current tz rule does this (the latest is 2010), and R-09 makes it reachable only through a manual entry dated 2010 or earlier in those zones. The lead should settle the rule in the ADR (key by bounds, or by local date with a clamp) before T2.4 relies on rows. No fixture was added because the expected value is undefined.
2. **The core can't represent the last ~26 hours of year 9999.** jiff's range ends at `9999-12-30T22:00Z`, so `format_instant(253402300799)`, `parse_instant("9999-12-31T23:59:59Z")` and `day_bounds(9999-12-31)` return errors. The server answers all three (`+010000-01-01T00:00:00Z` for the end of that day), and the contract accepts year 9999. Unreachable in practice: R-04 rejects future ends.
3. **Display above 2^53 differs.** The server throws `invalid-seconds` for 2^53, while the core formats it. Unreachable, and pinned up to 2^53-1 by a fixture.
4. **A gap that starts before midnight and ends after it is unit-tested in the core only.** No IANA zone has one, so the shared fixtures cannot pin it, and the server's IANA-only check rules out a synthetic zone. The server relies on Temporal's `startOfDay`. Accept as is, or add a server unit test against the polyfill's internals if wanted.

Also noted: the fixtures now use pre-1970 and historical tz data (LA LMT 1883, Kathmandu 1986, Apia 2011). Node's ICU (2026a) and jiff's bundled tzdb (2026e) agree on all of them today. It belongs on the ADR-0004 watch item: a tzdb release that revises old data could make one side disagree.
