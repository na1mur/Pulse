## Bugs

### Bug 1: Concurrent guesses bypass the per-account sign-in limit
- Severity: High (spec 9.1 "rate limits per IP and per account on auth operations", a deliverable of the task row; review focus "rate limits cannot be bypassed").
- Cause: `SessionService.login` checks the limit with `enforceUnder` before the hash and counts the failure with `hit` after it. Every request that arrives while the first one is hashing (about 30-50 ms, longer once the 4-thread pool queues) passes the check.
- Steps: verify an account; send 100 `POST /v1/auth/login` with wrong passwords at the same moment (live: `Promise.all`, a different `X-Forwarded-For` each with TRUST_PROXY=1, i.e. 100 clients). Also 30 at once from one client IP.
- Expected: at most 10 answers are password verdicts (401); the rest 429.
- Actual: live 100 x 401 from 100 clients, and 30 x 401 from one client (that client's own limit is the only cap). In-process: 40 of 40 (qa spec, `it.fails` "allows no more than 10 wrong-password verdicts ...").
- Impact: the per-account limit, the one meant to stop distributed guessing, only holds against an attacker who waits for each answer. With N addresses an attacker gets 30 x N guesses per 15 minutes on one account instead of 10.
- Fix direction (engineer's choice): reserve the attempt before the hash (count it with `hit` up front and give it back with `reset`/a decrement on success), so the 11th concurrent attempt is refused before it is verified. Keep the "unknown address limited like a known one" property.

### Bug 2: Flooding the rate limiter evicts a blocked account's failure counter
- Severity: Medium (rate-limit bypass; review focus "... or by unbounded memory growth": the bound was added, its eviction is the bypass).
- Cause: `RateLimiter.makeRoom` drops the oldest window when 10 000 are held and none has expired. The windows of every rule and every key share one table, and an account's failure window is opened by its first failure, so it is among the oldest. `resendVerification` creates two new windows (client, account) per request with no hash and no mail for unknown addresses, so it is a cheap filler; each IPv6 /64 is a fresh client.
- Steps: block an account with 10 wrong passwords (11th answers 429); send 5 000 `resend-verification` requests for distinct unknown addresses from distinct /64s (`2001:db8:0:N::1`, TRUST_PROXY=1); guess again within the 15 minutes.
- Expected: 429.
- Actual: 401, a fresh verdict; the counter starts again at zero (qa spec `it.fails` "keeps an account blocked ... when other clients flood the limiter", 3.4 s for the flood in-process).
- Impact: an attacker with an IPv6 /48 (free from tunnel brokers, common at hosters) can reset the per-account limit every few seconds: tens to hundreds of times the intended guess rate. The class comment ("frees an attacker's own counters at worst") does not hold.
- Fix direction: never evict a window that is currently refusing (or that holds an account's failure count) before cheaper ones; e.g. separate bounded tables per rule with the account-failure table evicting only expired entries, or refuse new low-value keys (fail closed for the flood) when the table is full of live windows.

### Bug 3: A stranger's later sign-up takes over a pending account the owner then verifies
- Severity: Medium (security; the account is new and empty, and a password reset in T1.6 would end the stranger's sessions, so the damage is bounded, but the stranger holds a signed-in session on the owner's verified account until then and the owner cannot sign in).
- Cause: by design "the latest sign-up of an unverified address wins" (`createOrRefreshIn` sets the new password and replaces the link). That defends against a squatter who registers first, and opens the mirror case when the stranger registers second.
- Steps (live and in the qa spec): owner registers `X` with P1; 61 s later a stranger registers `X` with P2 (204); the owner's inbox now holds two mails with the identical subject "Confirm your email"; the owner's own link answers 400 (it was replaced), the newest one 204; login with P2 answers 200, with P1 401.
- Expected: someone who does not control the mailbox never ends up with a password on a verified account.
- Actual: the stranger is signed in to the owner's verified account.
- Note for the lead: this is a design trade-off already decided in the build (squatter vs late stranger), so the fix likely needs an owner decision. One option that closes both: a re-sign-up of a pending address never changes its password (it may resend the link, rate limited), and the squatter case is solved by password reset (AUTH-07, T1.6), which proves the mailbox and can verify an unverified account. Another: bind the password hash to the token, so a link sets the password it was issued with, and keep the owner's link valid (still leaves the "owner clicks the stranger's mail" case open).

### Low notes (log only)
1. Tag order: the first `completeFirstSignIn` answer lists the tags in TAG-07 order; a later setup command (other device, other command ID) answers `listLive` ordered by `created_at, id`, which for tags created in one statement is random UUID order. Same set; clients should not rely on order, but the two answers to "the starter tags" differ.
2. Refresh has no grace for a lost answer: a device whose refresh response is lost (mobile network, killed app) and that retries with the old token is treated as a thief and signed out of that device. Strictly matches "reuse revokes the family"; worth a conscious decision before the Android client (offline-then-reconnect risk).
3. Device IDs as a sign-out lever: anyone who learns another user's install ID can sign in to their own account with it and delete that device row and its credentials (the T1.1 backlog decision). IDs are random UUIDs not shown to others today; keep them out of anything shared.
4. Passwords: the 8-128 rule counts UTF-16 code units (`z.string().min(8)`), so four emoji pass as 8 characters, and passwords are not Unicode-normalised (an NFC and an NFD spelling of `café` are different passwords).
5. The 200 ms register floor hides the paths only while the slowest path stays below it; under load (Argon2 queueing on the 4-thread pool) the new-address path would exceed it first. Acceptable for one household (D-11); a note for later load testing.
6. Future collision (not reachable in T1.5): `completeFirstSignIn` inserts the starter tags without checking existing names; once tag creation exists (T2.x), a user who creates "Deep Work" on one device before another device finishes setup would hit the unique index and fail setup every time. T2.x should handle it.

## Bugs

Low note (log only):
- R2-1 (Low): a window one guess under its limit can still be evicted. When every other window of `login-failures-account` is at its limit, the victim's window (at 9) is the only one that may go, so one new address evicts it and the victim gets a fresh count: 9 guesses per filler request for as long as the table stays full (`qa-rate-limiter.spec.ts` pins 45 guesses in 5 cycles). The class note's "can never unblock an account" holds for a blocked account (10), not for one at 9. The precondition is the one in the BACKLOG Medium (about 100 000 hashed login attempts from 3 334+ /64s per 15 minutes to hold 10 000 windows at the limit), which also saturates the 4-thread Argon2 pool on this hardware, so the extra guesses come at the cost of a visible outage. Fold it into that BACKLOG item when it is revisited (for example, never evict a window that holds an account's failures before its end, and fail closed instead).
