## Bugs

### Bug 1: dependency-cruiser drops every npm import that resolves into a `dist/` or `build/` folder
- **Severity:** Medium
- **Affected criterion:** the brief and ARCHITECTURE section 5 (dependency-cruiser rules mirroring section 2 run in `pnpm verify`). Rules affected: `server-not-to-dev-dep`, `no-non-package-json`, `desktop-ui-no-network` (for example `ofetch`, which resolves under `dist/`, and `socket.io-client`, under `build/`), and the kysely half of `server-domain-pure` and `server-transport-no-database` (kysely ships from `dist/`).
- **Steps to reproduce:**
  1. Add `apps/server/src/qa-devdep.ts` containing `import { describe } from 'vitest'; export const d = describe;`.
  2. Add `apps/server/src/qa-undeclared.ts` containing `import tseslint from 'typescript-eslint'; export const t = tseslint;`.
  3. Run `pnpm exec depcruise --config .dependency-cruiser.cjs apps`.
- **Expected:** `server-not-to-dev-dep` and `no-non-package-json` errors.
- **Actual:** no violation. With `--output-type json` the vitest import is missing from the module's dependencies entirely.
- **Cause:** `options.exclude.path` `'(^|/)(dist|build|target|coverage)/|...'` also matches the resolved files inside `node_modules` (`node_modules/.pnpm/vitest@.../node_modules/vitest/dist/index.d.ts`). Excluded modules and the edges to them are removed before the rules run. Packages whose entry file is outside `dist/` (for example `prettier`, `@nestjs/common` and `@tauri-apps/api`) are still checked, which is probably why slice 6's probes passed.
- **Fix:** anchor the build-output exclusion to the workspace's own folders. Checked in a scratch copy with a wrapper config: `'^(apps|packages)/[^/]+/(dist|build|coverage)/|(^|/)target/|^apps/(android|desktop/src-tauri)/'` reports all three probes, and the clean tree still passes ("no dependency violations found, 22 modules"). `.dependency-cruiser.cjs` is not on the edit guard's protected list. Also add a regression probe for an import that resolves under `dist/`, so this cannot come back.
- **Impact:** most boundary violations involving npm packages (dev dependencies in the server image, undeclared dependencies, some network clients in the UI, database access from the domain or controllers) would pass the check unnoticed.

### Bug 2: `pnpm verify` fails in a fresh clone on drive C:
- **Severity:** Medium
- **Affected criterion:** Done when: "A fresh clone installs and passes all checks with one command". It holds for the owner's clone on D: but fails for a clone anywhere on C:, which is the usual place on Windows (`C:\Users\<name>\...`).
- **Steps to reproduce:** clone the repo anywhere on C: (outside the OS temp folder) and run `pnpm verify`.
- **Expected:** all steps pass.
- **Actual:** `[docs] hook and script tests` FAILED in `.claude/hooks/guards.test.js:123`, "blocks recursive deletes outside the repo and temp dir", with `AssertionError: cmd //c rd /s /q C:\Users` (actual false, expected true).
- **Cause:** in the Bash test command, `C:\Users` unquoted becomes the drive-relative `C:Users`, which resolves against the repo when the repo is on C:. The guard is right to allow it, since `rd` would then delete `<repo>\Users`. The test data assumes a repo on another drive. A direct guard run confirms it: with cwd `C:\...\pulse` it exits 0, with cwd `D:\Personal\Hobby Projects\Pulse` it exits 2 (`scratchpad/qa-tools/guard-drive.cjs`). The case predates T0.2, but T0.2 made the hook tests part of the one command.
- **Fix (test data only, guard unchanged):** quote the path so it stays absolute, for example `'cmd //c rd /s /q "C:\\Users"'`, or build it from a drive that differs from `repoRoot`'s.
- **Related (Low):** with the clone inside the OS temp folder, `rm -rf ../other-project` also resolves inside the temp folder and is allowed. This is unrealistic for real clones and only a note.

### Low (log only)
- **L1:** CLAUDE.md "Lint" gives `pnpm exec depcruise --config .dependency-cruiser.cjs apps packages`, which fails until `packages/` exists (T0.4). `check.mjs` filters out missing roots, so `pnpm verify` is unaffected. Fix: use `apps` only for now, or note it. **Fixed in iteration 2** (see the round 2 re-test).
- **L3 (for T0.3):** `check-docs.sh` checks commit hashes cited in `docs/AGENTIC_SETUP.md`, so a shallow CI checkout (`actions/checkout` defaults to depth 1) or a source tarball fails the docs step. CI needs `fetch-depth: 0`.
- **L4 (for T0.3):** `rust-toolchain.toml` lists only `x86_64-pc-windows-msvc` as a target, so a Linux runner also downloads that std. Harmless but slower.
- **L5 (out of scope, existing before this task):** about 175 tracked `.claude/` files are CRLF on disk in this working tree while the index has LF. They are not part of the change and a fresh clone gets LF. Worth a `git add --renormalize`/checkout some time.

## Commit conditions
- Stage `gradlew` as executable: `git update-index --chmod=+x apps/android/gradlew` after `git add`. Otherwise Linux CI and Linux developers get "Permission denied", since `check.mjs` runs `apps/android/gradlew` directly. This is Medium if missed.

## Not run
- A clone on drive D: outside the scratchpad (I write only to the scratchpad). That case is covered indirectly: the repo itself on D: passes the hook and docs steps, and the clone passes every other step.
- A machine with empty caches (pnpm store, `~/.cargo`, `~/.gradle`): network download paths, the foojay JDK download and the Gradle build-cache miss path were not exercised.
- Linux or macOS: POSIX `gradlew` executable bit, `bash` without Git Bash, case-sensitive paths. The POSIX wrapper was run from Git Bash on Windows only.
- `tauri build` release and installers (T0.7), and CI (T0.3).
