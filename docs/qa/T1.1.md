## Bugs

### Bug 1: Case-insensitive email uniqueness depends on the database locale
- Severity: Medium (spec section 6 invariant: email unique, case-insensitive; the review focus names Unicode).
- Steps: create a database with `create database x template template0 encoding 'UTF8' locale 'C'`, run migration 0001, insert `JÉRÔME@example.test` and then `jérôme@example.test` (also `ИВАН`/`иван`).
- Expected: second insert fails with `users_email_key` (23505).
- Actual: both succeed (ASCII still folds). On `en_US.utf8` (the bundled alpine image) it works, which is why the engineer's tests pass. Spec section 10 allows an external database, whose locale the project does not control.
- Impact: two accounts whose emails differ only by non-ASCII case; sign-in lookup by `lower(email)` would pick one nondeterministically or fail. Fix options (engineer's choice): store an app-computed `email_key` (like `tags.name_key`, folded in JS) with the unique index on it; or make the migration or startup fail fast when `lower('É') <> 'é'`. Test `it.fails('keeps non-ASCII emails unique ...')` flips to red when fixed (remove the `.fails` then).

### Bug 2: Server crashes when PostgreSQL closes an idle pooled connection
- Severity: Medium (restart, failover or proxy idle timeout takes the whole API and realtime layer down; the contract has an `UNAVAILABLE` error code for this).
- Cause: `createDatabase` builds a `pg.Pool` with no `pool.on('error', ...)` handler; node-postgres re-emits idle client errors on the pool and an unhandled `error` event is fatal.
- Steps: start `node apps/server/dist/main.js` with a scratch DATABASE_URL, then run `select pg_terminate_backend(pid) from pg_stat_activity where datname = '<db>' and pid <> pg_backend_pid()`.
- Expected: the error is logged, the pool discards the client, the next request reconnects.
- Actual: uncaught exception; `curl /health/live` afterwards gives no response; process exited (Node dumps the pg client object). Reproduced once, deterministic from the code (no listener).
- Fix: attach an error listener to the pool in `database.factory.ts` (log with context) and add a test that terminates the backend and then queries successfully.

### Bug 3: Unreachable database gives an empty error message (Low)
- `DATABASE_URL=postgres://u:p@localhost:1/pulse node dist/main.js` prints `AggregateError [ECONNREFUSED]:` with a stack trace and no host, port or hint. Startup should say which host:port it could not reach (without the password), like the test helper already does.

### Bug 4: Revision counter can be lowered by delete + reinsert (Low)
- `delete from user_revisions where user_id = X; insert ... revision = 0` succeeds, bypassing the "only increases" trigger. Needs superuser-level access to the application's own role in practice, so only a code bug would hit it; consider restricting in the repository layer (T1.3+) or a delete-prevention trigger.

### Bug 5: App-level checks the database does not make (Low, for T1.2 and T1.3 to cover)
- Email accepts leading/trailing/blank whitespace and is not NFC-normalised (`café` composed and decomposed are distinct); timezone accepts any string; credentials accept `expires_at < issued_at` and a family spanning devices; a used email token's expiry and hash can still be edited; tag `name_key` is unchecked against `name` and a blank tag name is allowed. None violates a stated spec invariant; the validating layer (contract schemas, services) must own them and have tests.

### Bug 6: Docs claim `pnpm verify` never needs a database (Low)
- `CLAUDE.md` line 21 ("`pnpm verify` and CI never use it") and `docs/DEVELOPMENT.md` line 7 are now untrue: `pnpm verify` (and the `auto-commit` gate) fails without a reachable PostgreSQL unless `PULSE_SKIP_DB_TESTS=1` is set, and CI runs a postgres service container. The new "Integration tests" section is correct; the old sentences and the CLAUDE.md prerequisites list need updating (PostgreSQL on localhost:5432 or `PULSE_TEST_DATABASE_URL`). `scripts/dev.test.mjs` was retitled but its assertion still only checks the vitest config.

## Bugs
No Critical, High or Medium bugs.

Low notes (log only, no action needed to approve):
- R2-1 (Low): `emailKey()` lower-cases, it does not case-fold. `ΑΣ@x` becomes `ας@x` (final sigma) but `ασ@x` stays `ασ@x`; `STRASSE` and `STRAßE` stay distinct; `İ` keeps its combining dot. Those pairs are separate accounts. Deterministic, the doc comment says "lower-case", and it matches what `lower()` did on a UTF-8 locale; it only matters for non-Latin or Turkish local parts. The unit spec records the behaviour.
- R2-2 (Low): trim runs before NFKC, so 50 spacing marks (for example U+00A8) give a key with a leading space that is not a fixed point (`emailKey(emailKey(x)) != emailKey(x)`). Harmless while `emailKey()` is applied only to the typed address, as the documented contract says; it would drift if applied to a stored key. U+200B (zero width space) is not trimmed by JavaScript, so `a@x.test` and `a@x.test` plus U+200B are different accounts. Email format validation (T1.2 contract schema, T1.4) should reject control, format and whitespace characters.
- R2-3 (Low): an unencoded `@` in the password makes the URL parse as another host, so the hint reads `Cannot reach the database at ss:5432`. That names the host tried, which is a useful clue, but there is no hint about percent-encoding. Startup errors still end as an uncaught exception with a stack trace and the Node version banner (the message itself is now clear).
- R2-4 (Low): a database that already ran the old 0001 is refused with `migration 0001 (accounts) changed after it was applied; add a new migration instead`, which is wrong advice for that one case. The task report says to use `pnpm dev:reset`; neither the message nor DEVELOPMENT.md ("Database and migrations") says so. No such database exists here (the dev `pulse` database has no `schema_migrations`).
- Carried over from round 1, unchanged and accepted as app-level or Low: Bug 4 (revision counter delete and reinsert), Bug 5 (timezone name, credential dates, token expiry edits, `tags.name_key` unchecked).
